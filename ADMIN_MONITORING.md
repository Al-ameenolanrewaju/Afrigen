# Admin monitoring

The admin command centre is available at `/admin/command-centre`. Its routes use
the existing `admin_required` authorization, and incident changes are protected
by Flask-WTF CSRF.

## Collected checks

When the existing APScheduler is enabled, the monitoring cycle runs every
minute. It records five-minute, idempotent snapshots and keeps 90 days of
history. Re-running a cycle within the same five-minute bucket updates that
bucket instead of adding duplicate snapshots. A UTC daily report is generated
at 00:05 and can also be generated by an administrator from the Command Centre.

The current checks use persisted application data:

- Database query probe (`SELECT 1`).
- Processing and pending generations older than configured thresholds, recent
  failed generations, and completed image, video, and audio generations from
  the last 24 hours checked for a recorded output URL. No prompts or output
  content are read or stored.
- Persisted provider-health state and recent provider request outcomes. This
  does not make live provider calls.
- Recent payment webhook signature and outcome records. Raw webhook payloads
  are not copied into monitoring history.
- Pending/retrying work in the existing connected-account and social publishing
  queues.
- Database connection-pool utilization when exposed by the active driver.
- Confirmed payment records and totals for the current and previous 30-day
  periods; no forecast is included.
- Recorded generation costs and provider-log estimates shown separately.
- Credit-ledger consumption above a configurable 24-hour review threshold. This
  is an investigation signal only; it never suspends an account. The incident
  retains up to 25 internal account IDs and amounts spent for administrators.
- Host-local disk usage, Linux memory usage when `/proc/meminfo` is available,
  normalized one-minute load when the operating system exposes it, and an
  optional linear disk-capacity estimate after at least six hours of history.
  The estimate is explicitly a trend, not a guarantee or a fleet-wide measure.

The migration adds indexes for the high-volume generation, provider-log,
payment, webhook, and credit-ledger queries used by these checks.

An active monitor condition creates or updates one incident for that monitor.
Occurrences and first/last-seen times are retained; healthy checks resolve
active incidents. A persisted timeline records detection, severity changes,
recovery, reopening, acknowledgement, assignment, status, and note changes.
Administrators can assign, add a note, acknowledge by updating the incident,
and move incidents through Open, Investigating, Identified, Resolving,
Resolved, and Closed.

The daily report contains UTC-day signup and generation counts, recorded
payment totals, recorded generation costs, provider-log cost estimates
separately marked as estimates, and current incident counts. Its recommendations
are actions from active incidents; it does not invent forecasts, churn
predictions, or acquisition costs. Payment totals reflect rows in the local
payment table and should be reconciled with the payment-provider ledger before
financial decisions.

## Optional thresholds

All settings have defaults; no new environment variable is required:

| Variable | Default | Purpose |
| --- | ---: | --- |
| `MONITORING_STUCK_GENERATION_MINUTES` | `15` | Processing age that marks a generation check critical |
| `MONITORING_PENDING_GENERATION_MINUTES` | `10` | Age before a still-pending generation is flagged for review |
| `MONITORING_PENDING_GENERATION_CRITICAL_COUNT` | `10` | Stale pending generations required for critical severity |
| `MONITORING_GENERATION_FAILURE_RATE_WARNING` | `0.25` | Failure-rate warning when at least 10 generations are present |
| `MONITORING_PROVIDER_FAILURE_RATE_WARNING` | `0.5` | Recent provider-log failure-rate warning when at least 10 requests exist |
| `MONITORING_WEBHOOK_INVALID_SIGNATURE_CRITICAL` | `1` | Invalid signatures required for a critical webhook incident |
| `MONITORING_WEBHOOK_FAILURE_WARNING` | `1` | Failed webhook outcomes required for a warning |
| `MONITORING_QUEUE_BACKLOG_WARNING` | `20` | Combined outstanding queue work warning threshold |
| `MONITORING_DB_POOL_WARNING` | `0.75` | Connection-pool utilization warning fraction |
| `MONITORING_DB_POOL_CRITICAL` | `0.9` | Connection-pool critical fraction |
| `MONITORING_CREDIT_BURN_WARNING` | `500` | Credits spent by one account within 24 hours before review alert |
| `MONITORING_RESOURCE_WARNING_PERCENT` | `85` | Host disk or available Linux memory utilization warning |
| `MONITORING_RESOURCE_CRITICAL_PERCENT` | `95` | Host disk or available Linux memory utilization critical threshold |
| `MONITORING_DISK_PATH` | Current working directory | Filesystem mount whose capacity is measured |

## Deployment

1. Apply the additive schema migration before starting application workers:
   `flask db upgrade`.
2. Keep `ENABLE_SCHEDULER=true` on exactly one application process. If the
   deployment runs multiple web workers or replicas, disable the in-process
   scheduler on all but one process to avoid duplicate monitoring work.
3. Check `/admin/command-centre` after the first monitoring cycle, or use
   **Run checks now** to collect an initial snapshot.

Run focused tests with:

```text
pytest tests/test_admin_monitoring.py -q
```

## Known coverage gaps

The application does not currently provide reliable event sources for backup
integrity, deployment impact, host-wide CPU/memory utilization on every
platform, validated output contents or quality for every provider, cancellation
prediction, customer lifetime value, acquisition cost, complete user journeys,
accessibility, geographic performance, or durable admin/security audit and
rate-limit events. These are not shown as measured capabilities in the command
centre. Host measurements cover only the current application process's local
filesystem and Linux memory/load where available, not an entire deployment.
The provider check reflects persisted health/request logs, not an end-to-end
probe; payment webhook inspection is bounded to the newest 1,000 records in its
one-hour window. Alert acknowledgement is stored on the incident, but outbound
notification channels, quiet periods, and escalation policies are not yet
implemented.
